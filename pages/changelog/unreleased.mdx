# Upcoming changes

<Callout type="info">
These are the current notes for the next stable release, covering changes since v1.2.241. They're updated as work is merged, so a development build may not include every change listed here. When the release ships, they become its notes.
</Callout>

## Added

- **Make your own Message gate options**: besides Off and Follow guidance, a chat's Message gate can now use an option you make. Choose **Create option…**, describe in plain words which messages should wake the agent, wait or be dropped, and the Gate Option Assistant writes the rules. Every option is tested on 240 sample messages before you can save it: it must never hold or drop a message that needs the agent, and never drop one it shouldn't. A new option starts in **Try first**, which only records what it would have done, until you turn it on. Options are shared by all your channels; editing one updates every chat that uses it, and a deleted option lets every message through. Agents can list and check options with `@realtimex/pp-cli` 2.0.71 or later, and set one with `set-channel-gate --option`. Only you can save or delete options. Gate presets made by hand in a workspace's `.realtimex-decisions` folder no longer apply to the Message gate.
- **Settings → System Logs warns before a Mac runs out of terminals**: RealTimeX now counts the pseudo-terminals it holds on macOS and Linux against the system's limit. When it holds 80% of them, System Logs shows a warning under the new "terminal" source, and another at each further 5%. If a terminal, task or channel reply can't start because none are left, System Logs says that the limit is reached and that restarting RealTimeX frees them, instead of showing only the start failure. That entry is written at most once a minute. RealTimeX never stops or refuses a terminal because of this count.
- **Agents can save a website read and run it again**: with agent-browser 0.42.0 or later, an agent that read data from a site in the RealTimeX Browser can save that read as a flow. Later it runs the flow with new values, for example another search term. A run sends the site's own data requests instead of opening and reading the page, so a repeated lookup takes much less time and fewer tokens. Each workspace keeps its own flows, so client workspaces never see each other's. Flows store no cookies: a run uses the sign-in of the browser session it runs in. If a flow stops working, the agent uses the page instead. Agents don't upgrade agent-browser on their own. With an older version they keep using the page and tell you that upgrading enables flows. An upgrade restarts the other agents' browser connections, and they reconnect before going on.

## Fixed

- **Terminal agents keep reporting after running for days**: on macOS, a terminal agent such as Claude Code that ran for about three days stopped reporting to RealTimeX. Its replies, permission cards and activity no longer reached the chat, and messages could wait behind a turn that never ended. macOS clears old files from its temporary folder, and RealTimeX kept the small helper each agent calls there. RealTimeX now keeps those files in its own data folder for Claude Code and Gemini, and puts back any that go missing while the terminal runs. Codex and Cursor already kept theirs elsewhere; Qwen Code, Copilot, Devin, Grok and Antigravity follow in a later update. Terminals started before you update keep the old behavior until they restart. A reply that was already lost is not recovered. RealTimeX also removes these folders when the RealTimeX that made them has closed and they are more than a week old.
- **Agents no longer talk over staff, send twice, or report garbled text as sent**:
  - On Pancake, a send is refused when staff wrote in the chat after the agent last read it. The agent gets the staff's new messages instead, and its next send goes through.
  - Every message or file an agent sends has a send id. When the channel doesn't confirm a send, the agent can check later whether it arrived (Pancake looks it up in the conversation), and a retry never posts it twice. Each channel shows how many sends went unconfirmed and how they ended.
  - A thread-to-thread message that the receiving terminal confirmed late was delivered up to four times. It now arrives once, and the sender is told the outcome is unknown instead of failed.
  - On Pancake, a file with a caption arrives as the file followed by its caption, and both message ids are returned.
  - Long Zalo messages are split at line breaks and arrive whole and in order. The chat history no longer shows long messages as single characters separated by commas.
  - Agents need `@realtimex/pp-cli` 2.0.72 or later for `get-channel-send-status`.
- **Claude Code and Gemini no longer stop at launch to ask about a workspace's extra folders**: since Claude Code 2.1.326, Claude asks "Adding a new directory … Is this a directory you created or one you trust?" at every launch for each extra folder it is given that it doesn't trust yet, and its default answer ends the session. RealTimeX gives Claude the extra folders your workspace's file access allows, so those terminals stopped before their first prompt and showed "Can't confirm that Claude has started". Answering in the terminal held only for that session. Gemini CLI asks a similar question about the folders it is given. RealTimeX now records that yes for each of those exact folders before Claude Code or Gemini starts, as it already did for the workspace folder, in the login the terminal uses. A folder you told Gemini not to trust stays untrusted, also when you refused it through a link to it or to a folder around it, and RealTimeX never records a folder whose record would let Gemini trust a folder inside it you refused. Your disk, your home folder and any folder above it are never trusted this way, so the agent still asks about those. Qwen Code and Antigravity don't ask about extra folders, so nothing changes for them.
- **A RealTimeX Cloud computer with the Desktop add-on does in its web UI everything one without it does**: Desktop is an upgrade, but its web UI did less. Messages to Claude, Codex and other terminal agents from the chat now go to the computer, as they do without the add-on: the app on the computer's screen runs the agent and the answer shows in the chat. The "Terminal agents on this computer run in the RealTimeX app on its screen" note is gone. If the app on the screen is starting or restarting, the chat box says so at once and keeps your message to send again, and signing in to the web UI still completes. Settings changes from the web UI, such as creating a workspace or changing preferences, are accepted as without the add-on, and only the computer's own RealTimeX account can use its web UI. Typing `@claude …` without picking it from the @ menu now reaches Claude in any browser too, instead of being sent as ordinary chat and waiting forever. The web UI also gets everything else it has without the add-on, served by the app on the screen: watching and typing into agent terminals, Local Apps (start, stop, logs, ports), Terminal Agents' Accounts and Memory with account sign-in, Claude and Codex usage in the status bar, the version and About, agent CLI installs in Getting Started, importing an agent session, Open log and Open file, CLI path checks, and Privacy & Data.
- **A Messenger chat comes back to the agent after your staff mark it done**: after the agent handed a Messenger conversation to Page Inbox, RealTimeX kept it handed over even once staff marked it done. Every later customer message was stored without reaching the agent, and replies were refused, for as long as the customer kept writing. RealTimeX now checks with Meta before it holds back a customer message or refuses a reply: when Meta shows no owner, or RealTimeX as the owner, the next message reaches the agent again. A handover now ends 24 hours after it started unless Meta confirms that staff still own the conversation; new customer messages no longer extend it. A customer message held back during a handover now shows "Didn't reach the agent: this chat was handed over." under it in the thread, counts in Needs attention, and the agent hears about it on its next turn. Agents can take a conversation back with `channel-act takeBack` (taking it from staff needs Conversation routing on the Page), and `channel-act threadOwner` now tells "Meta names no owner" apart from "the owner couldn't be read".
- **Messenger chats show the customer's name**: Meta won't share most people's Messenger profile with the page's app, so their threads were named "Facebook Messenger · sender cu_5" and the agent and Access had no name for them. RealTimeX now takes the name the page's Messenger conversation shows. The agent gets it, and so do the person's record and the people you picked in Access (shown the next time you open Access). A thread that still has a "sender …" name takes the person's name with their next message; a thread you or an agent renamed keeps its name.

## Security

- **A server without a screen, and a RealTimeX Cloud computer, accept only their own web UI and programs with a credential**: a request that reaches the server through its web UI port is answered as your account only with your sign-in or an API key. Before, a request with no credential at all was answered as the signed-in account, so on a Cloud computer the address's password was the only protection. Another website's page can no longer read from or act on the server's API through the web UI port, including live connections. Signed-in browsers, the desktop app on the computer's screen and programs using an API key work as before.
