# Upcoming changes

<Callout type="info">
These are the current notes for the next stable release, covering changes since v1.2.197. They're updated as work is merged, so a development build may not include every change listed here. When the release ships, they become its notes.
</Callout>

## Added

- **RealTimeX Link can reopen RealTimeX after a crash**: RealTimeX now tells RealTimeX Link each time it closes on purpose: when you quit, restart it, install an update, log out or shut down. If RealTimeX closes without saying so, as in a crash, RealTimeX Link can reopen it. If RealTimeX's server stops and RealTimeX can't restart it after its usual attempts, RealTimeX closes itself so that RealTimeX Link reopens it, instead of staying on the "RealTimeX Server was down" notice; without RealTimeX Link watching, the notice stays as before. RealTimeX now includes RealTimeX Link 0.7.0, which does this: it reopens RealTimeX about 3 seconds after a crash, waits longer after repeated crashes, and stops after the 4th crash in 10 minutes until you open RealTimeX again. Turn it off in RealTimeX Link → Settings → **Reopen RealTimeX if it crashes** (on by default). RealTimeX Link now starts at login whether or not Remote Control is on, and on macOS it starts again by itself if it stops.
- **More of the desktop app in a headless server's web UI**: the web UI of a RealTimeX server without a screen now shows the parts of the desktop app the server can serve. The status bar is back at the bottom, with Claude and Codex usage, the terminal agents' count and memory, loops and the public address. The header shows the version, which opens About (build, device and listening ports), and the workspace's terminal, git, loop and remote-screen buttons. Terminal Agents has its **Accounts** and **Memory & Instructions** tabs, so you can add, pick, sign in again and remove Claude and Codex accounts on the server: the sign-in runs in a terminal on the server that you use from the browser. The Memory page lists the agents' memory too. Local Apps show whether they run, their logs (history and live) and ports, and start, stop and restart. **Privacy & Data** is in Settings. You can import an agent session, install or update agent CLIs from Getting Started and sign in to them there, and find or check a CLI's path. A setup command in Getting Started can be copied but not opened in a terminal from the browser. **Open log** and **Open file** open the server's file in a new browser tab, or download it when a tab could run it as a page (HTML, SVG and similar). If the page loses its connection to the server's agents and terminals for a while, it says so and offers Reload. Starting a terminal from the browser, recording, speech, screen capture, the RealTimeX Browser, the tray and in-app updates still need the desktop app.
- **Pick workspace skills from the `/` menu**: with a terminal agent such as Claude Code or Codex attached, typing `/` or pressing **Commands** in the chat box now lists the workspace skills that agent can use, next to the commands that work with it. Search by name or description; recently used skills come first. Picking a skill puts it at the start of your message, so you only type the request, and RealTimeX sends it in the form the agent understands: `/name` for Claude Code, `$name` for Codex, and a plain request to use the skill for other agents. The menu now shows only what works for the attached agent: `/image` and presets with the built-in model, `/stop` and `/terminate` with a terminal agent. A skill the agent doesn't have is marked before you send, and with no agent attached a skill can't be sent. **Manage skills** opens the workspace's Skills settings. Skills that only RealTimeX itself runs are not listed.
- **See your other desktops' work in the footer**: a desktop can now share its work status with your other desktops signed in to the same account. In Settings → Sharing → Desktop messaging, each connected desktop has a **Work status** block: **Share…** lists exactly what the other desktop will see (its terminal agents, open loops, roles, resources and limits; never whether you're at your desk, messages, questions, terminal output or files), and **Stop sharing** ends it. Turn on **Show your other desktops' work status here** on the desktop you look from. The Terminal agents and Loops popovers then name what needs a look on each other desktop and add a section per desktop, with its agents and loops read-only. When two desktops have a loop for the same issue, both rows say so ("Also on MacBook Air") and the Loops button counts it; nothing is stopped. Agents can ask you to share or stop sharing with `peer allow-status` and `peer deny-status`; nothing changes until you confirm. Before a loop starts, `rtx-loop start` now names the desktop that already has the issue and asks you to decide before starting a second one.
- **Agents can react, quote, label and hand Messenger chats to your staff**. In a Facebook Messenger chat the agent can react to messages, reply to a specific message, read the conversation, see the customer's name and picture, and add or remove your Page's labels. When a person should take over, the agent hands the conversation to Page Inbox and stays quiet until your staff hand it back or the chat is idle for a day. Creating or deleting labels and changing the Messenger menu or greeting ask you first. To hand over, set RealTimeX as the default app in your Page's Conversation routing settings.

## Changed

- **Apply a new Loop version while loops are running**: Loop settings no longer asks you to finish or end every loop outside a Project before you upgrade, switch or repair the global Loop. The confirmation now lists how many of those loops are running, the five most recently updated, and what changes for them: they keep the workflow and roles they started with, and their agents read the new version's role guidance from their next turn. Tick the box to confirm. If a loop starts or ends while you're reviewing, nothing is applied and you can review the updated list. Deploy topology, from the Topology editor or from the plugin's Configure, now saves your topology and, while loops are running, opens Loop settings so you can apply that version there. Deploying a topology you didn't change no longer asks you to apply it again. If the Loop's adoption record goes missing or is damaged, Loop settings still shows your current version and offers to apply it again, and starting a loop until then asks you to finish in Loop settings instead of failing with a server error.
- **RealTimeX now needs macOS 13 Ventura or later**: Macs on macOS 12 Monterey can keep using version 1.2.197, but won't get this update or later ones. A Monterey Mac on an older version may still say "Up to date". It keeps working but won't be updated.

## Removed

- **Agents in groups see every message again**: the **Agent turns per hour per group** limit is gone from Settings › Channels. Before, once a group used its hourly turns, the agent saw only messages that @mentioned it until the hour reset, so in a group where the agent decides when to post it missed what was said. Now every group message that the channel's access and reply settings let through reaches the agent, on every channel. Groups set to answer only @mentions still do. Send rate limits are unchanged. `realtimex-pp-cli update-channel --agent-turn-budget-per-hour` is still accepted but does nothing; agents need `@realtimex/pp-cli` 2.0.64 or later for the updated help.

## Fixed

- **The server no longer keeps a CPU core busy while terminal agents work**: RealTimeX kept rebuilding the terminal session history of a busy thread over and over. Every new terminal event restarted the rebuild, and a rebuild that new events overtook was retried at once, so the server used most of a core while agents worked. Each thread's history now rebuilds at most about once per four times its last build (between 1 s and 60 s), retries after a race back off up to a minute, and many busy threads together use at most about half a core. The history query also does about half the work (it compiles 24 times smaller). The session list can be up to a minute behind while a thread is busy; it keeps showing the last finished history meanwhile.
- **Cursor no longer gets stuck when it runs several commands at once**: when Cursor asked to run two or more commands at the same time, RealTimeX answered only the first "Run this command?". The others stayed waiting with no approval card, or ran without anyone deciding. Each command now gets its own approval, whether Runtime Auto-Approve or you decide it, and RealTimeX answers each one only while Cursor is showing that command's prompt. Cursor's prompt now starts with a short code such as `[#1a2b3c4d]` that RealTimeX uses to tell the prompts apart.
- **A message of several lines to a new Cursor terminal is sent, not left typed**: when a new Cursor terminal's first message had more than one line, such as a loop handoff, it often stayed typed in Cursor's message box and was never sent. The terminal then did nothing until someone pressed Enter in it or the next message arrived. RealTimeX sent the message about 2 seconds after starting Cursor, while Cursor could still be starting and ignored the Enter. It now waits until Cursor is ready for your message. If Cursor never says it's ready, the message is sent after 30 seconds. One-line first messages and later messages were not affected.
- **A loop whose agent is waiting on you counts in Needs you**: when the agent whose turn it is waits on a question to you, its loop now joins **Needs you** in the footer's Loops popover and counts in the button's label, after the loops waiting on you by their state. While a footer popover is open, agent and loop states now refresh every 5 seconds.
- **Agents no longer ask whether to trust their own workspace folder**: every terminal agent RealTimeX starts works in the workspace's folder, which RealTimeX created, and many of them asked "Do you trust this folder?" there the first time, including in a new workspace or on a new computer. The terminal did nothing until someone answered, and answering stopped it from taking automatic messages. RealTimeX now records that yes for that exact folder before the agent starts: Claude Code, Codex, Gemini, Qwen Code, Cursor, Devin, Antigravity, Grok, GitHub Copilot, Kimi Code, Factory Droid, iFlow, Pi and the RealtimeX Agent. Each agent's own trust record is used, in the account it runs on or your own login, and nothing else in those settings changes. A folder you told an agent not to trust stays untrusted. Other folders, including folders you open yourself, still ask as before, except in Cursor, which RealTimeX already starts trusting the folder it opens in. Kiro still asks, even in the workspace folder. Codex is only affected inside a git project, where it would ask. Separately, trust you once gave your whole disk or home folder in one Claude login is no longer copied to your other Claude accounts.
- **Claude terminals on an added Claude account no longer stop on Claude's setup or trust screens**: after you added a Claude account in Settings, every Claude terminal started on it, including the ones RealTimeX reopens after an update, stopped on Claude Code's first-run screen ("Choose the text style that looks best with your terminal"), and then could ask "Do you trust this folder?" again for folders you had already trusted. The terminal did nothing until someone answered, and answering stopped it from taking automatic messages until it was restarted. RealTimeX now marks Claude's setup as done for each account, and a terminal on an account trusts the folders you already trusted in your other Claude logins on this computer. Folders you never trusted still ask once, as Claude always does. Accounts added earlier are fixed the next time a terminal starts on them. Your Claude sign-in and settings are kept.
- **A terminal that's waiting for you before it starts says so**: when Claude stops on a question before it starts, such as whether to trust the working folder, its card in the chat and its tab in the Terminals panel now show **Waiting for you**, with the question, the folder and **Open terminal**. When Claude asks about the folder the terminal was opened in, **Trust folder** answers it from the card; RealTimeX only says the answer was sent, and answering this way doesn't stop automatic messages the way typing in the terminal does. If RealTimeX can't confirm within 30 seconds that Claude has started, the card says so instead of showing it as running; agents that can't report their start show **Start not confirmed**. A chat message is never typed into such a question: if you send one while the question shows, it stays in the box with a note, and a message that was already waiting is marked as not sent. A message waiting behind the first reply now says it waits for the terminal to start, then to finish. Each terminal now shows as one card in its chat, and a terminal that stopped taking automatic messages says so once.
- **A pasted image reaches the agent on a cloud computer**: in the web page of a RealTimeX Cloud computer or another server without a screen, an image pasted into the message box now reaches the terminal agent as a file it can open. Before, the agent got only "[Image #1]" with no file, because the image was sent without a name and dropped. Files sent the same way were not affected.
- **Allow remote control off now keeps every computer out**: RealTimeX now includes RealTimeX Link 0.6.5. Before, turning off **Allow remote control** only refused new requests. A computer you had already let in could still connect through the internet for up to a day. Now it ends any live view at once and refuses every computer, including ones you let in before. When you turn it back on, those computers can connect again without asking. Agents in RealTimeX on this computer keep working either way.
- **Agents use this computer from chat threads with accented names**: an agent in a thread whose name has letters such as "ó" or "Đ", like a Zalo group's chat, couldn't take screenshots, click or type on this computer, or read apps by their controls. Every command failed with "X-RTX-Caller is required". It now works whatever the thread is called, and RealTimeX Link's activity log shows the thread's name as it is.
- **QA failures can return directly to Dev in older coding loops**: a failed QA result now keeps its failed state when handed back for fixes. The loop no longer rejects it because Dev has more actions available after a passing result, or suggests reporting a pass instead. A role that cannot act on the result is still refused, with suggestions to send that same result to another role.
- **Linux updates ask for your password every time**: after an update or a restart, RealTimeX could start again in a state that can't ask for an administrator's password. Its next update then quit without asking and opened again on the old version. RealTimeX now starts itself again in a way that keeps the password prompt, and a copy that was started the old way still asks before it installs. If you cancel the prompt or the install fails, RealTimeX opens again on the version you had and says why: the password prompt was closed, no administrator's permission could be had, or the installer reported an error. The next update asks again.
- **RealTimeX Link updates itself on Linux** (realtimex-link 0.6.3 and 0.6.4): RealTimeX now includes RealTimeX Link 0.6.4. On Linux, Update in RealTimeX Link now asks for your password and installs the new version in place, instead of opening the download page. If the update can't be installed, RealTimeX Link says why and keeps the version you had. On Windows, links from RealTimeX Link open in your browser more reliably.
- **Pancake chats no longer stall or lose customer messages after an unreadable message**: when a Pancake customer sent something RealTimeX could not read, such as a card Pancake returns without its text, the chat could get stuck, and everything the customer wrote in the next ten minutes or so was never delivered to the agent, without any error. These messages now pass without blocking the chat, the customer's next message reaches the agent, and the unreadable one appears in the System Log as a warning. Comment conversations no longer make Pancake webhook deliveries fail, and when a Pancake sync fails for a reason other than a Pancake request, the System Log now shows the real error instead of "Pancake request failed".
- **Loop and agent status no longer contradict what the agent is doing**: when a loop hands work to an agent that was asleep, the Loops popover now shows the handoff as started once that agent wakes up and picks it up. Before, it said the handoff "didn't start" while the same popover showed the agent working on it. A loop no longer counts as started just because its first handoff was delivered; it starts when an agent picks the work up. An agent that RealTimeX reopens after a restart no longer shows as exited or "Not running" for its first few seconds; until it is running, its state reads as unknown.
