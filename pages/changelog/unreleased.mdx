# Upcoming changes

<Callout type="info">
These are the current notes for the next stable release, covering changes since v1.2.156. They're updated as work is merged, so a development build may not include every change listed here. When the release ships, they become its notes.
</Callout>

## Added

- **Test a Pancake page with a few people before opening it to everyone**: a Pancake page can now use "Only people I pick". In Access, choose people from the page's latest conversations (with Load more and a name filter). The agent answers only them; everyone else gets no reply, and their conversations stay unread for your staff. "People I approve" is no longer offered for Pancake: pages that used it switch to "Only people I pick", and the people you had approved keep access. The agent also no longer marks Pancake conversations as read. Agents can pick conversations with `@realtimex/pp-cli` 2.0.60 or later.
- **Agents control this computer the same way as another one**: an agent asked to work on the computer it runs on can now take screenshots, click, move the pointer, type, press keys, scroll, wait for the screen to change, use the clipboard and send or fetch files there, not only read and use apps by their controls. It works even when **Allow remote control** is off, and without Tailscale or the internet relay, because it goes through RealTimeX to this computer's own RealTimeX Link. When you say "this computer", "here" or "my computer", the agent uses it straight away instead of asking which saved computer you mean; it asks only when you named none and several are saved. Your pointer and keyboard focus move while the agent works, so it stays in the apps the task needs. Each action is recorded in RealTimeX's System Log, without the text typed. This needs RealTimeX Link 0.6.2 or later on this computer, which RealTimeX now includes; with an older Link the agent is told to update RealTimeX Link, and reading apps by their controls keeps working. RealTimeX also notices when RealTimeX Link gains a feature while RealTimeX is running, such as after an update, instead of only at start.
- **Agents can set up existing channels without opening Settings**: an agent can now change everything about a channel that Settings › Channels can: who can use it in private chats and groups, the people you pick and the contacts whose groups turn on by themselves, each group's or chat's reply mode, guidance and workspace, group name rules, slash commands, send limits, the turn budget and human-like pacing. It can list a channel's people, pause, resume or remove one, list access requests and reject or stop ignoring them, look up the account's friends and groups by name, and move a channel to another workspace. Limits stay within the same ranges as in Settings. When an agent is answering an outside chat, anything that would let more people in, loosen a limit, change a token or delete a channel waits for you in the usual permission prompt on the desktop, never in the chat. An agent working in a client-isolated workspace can now manage that workspace's own channels, but never another workspace's. Agents need `@realtimex/pp-cli` 2.0.59 or later.
- **Connect a desktop that's signed in to another account**: in Settings → Sharing → Desktop messaging, Connect another desktop now asks which account the other desktop is signed in to. Choose **Another account** for a desktop that uses a team or service account on purpose, such as a Mac mini that hosts client workspaces. The invitation shows this desktop's account to whoever uses it, and when another desktop uses it, you confirm that desktop by its name and account here, within 10 minutes, before anything connects; the other desktop waits until you do. After connecting, nothing is open on either desktop: each owner allows workspaces on their own desktop with **Allow messages and tasks**, and replies to messages you sent still arrive. Settings and agents' desktop lists name the other account, and either side can disconnect. Client-isolated workspaces stay unreachable from every desktop; agents set them up through a regular workspace on that desktop. Agents ask for such an invitation with `peer connect --other-account`. Both desktops need this version of RealTimeX.
- **Agents can tag, assign and update the customer in Pancake chats**: an agent answering a Pancake customer now gets the `channel-act` command. On that customer's conversation it can add and remove tags, assign the conversation to staff, mark it read or unread, read the conversation's history from Pancake, read the customer's profile, update their name, phone numbers, birthday and gender, and add, edit or delete customer notes. It can list the page's tags and staff first, and `--reply-to` now quotes a customer's message. Page-wide data such as statistics, ads, the customer list, posts and call logs asks you first in the usual permission prompt. Comments, WhatsApp templates, other conversations and page credentials stay off limits. Staff see every change in Pancake right away. Assigning a conversation does not stop the agent; a staff reply still does.
- **Agents use apps by their controls, pick screens and windows, and handle errors reliably**: the Remote Control skill can now list a computer's screens and take a screenshot of any of them, list its open windows and bring one to the front, and wait until the screen changes instead of pausing for a fixed time. After an agent looks at one screen, its clicks go to that same screen. Every command now answers in one consistent format that tells the agent whether it may retry and whether an action may already have happened, so it no longer repeats a click that might have landed. Each agent action on another computer, and each failure, is now recorded in RealTimeX's System Log with the agent's workspace and thread, without any typed text. Windows, screen choice and waiting need a RealTimeX Link version that supports them on the controlled computer; with an older Link the agent is told to ask for an update. When an agent connects, the other computer's live view now opens in its chat; before, the request to open it was refused. Agents can also read an app's buttons, fields and menus by name and act on them directly, such as clicking a button, filling a field or ticking a box, on another computer or on the computer they run on. That's more reliable than clicking at screen positions, and agents fall back to clicks when an app doesn't support it. Password fields are never shown to the agent. On the computer it runs on, an agent can read and act on apps the same way, but it can't use the mouse, keyboard, screenshots, clipboard or files there. These commands run in the agent's terminal, so the terminal's usual approval and Runtime Auto-Approve apply; there's no separate approval for apps. Every action an agent takes there is recorded in the System Log. A screen is now chosen by its number as `n:2`, so it can't be mistaken for a screen id. These need RealTimeX Link 0.6.0 or later, which RealTimeX now includes. Scripts that read the skill's old output can set `RTX_RC_OUTPUT=legacy` for one release; that option will be removed in the release after.
- **Agents can do almost everything in WhatsApp and Telegram chats**: an agent answering a WhatsApp or Telegram chat now gets the same `channel-act` command as on Zalo Personal. On WhatsApp it can run polls, share locations, contacts, stickers, videos and voice notes, edit, delete, pin, star and forward messages, and manage the group: add, remove, promote or demote people, change settings, the name and the invite link. On Telegram it can send photos, files, polls and stickers, edit, delete, pin, forward and copy messages, and moderate the group (ban, restrict, promote, invite links, title and forum topics), as far as the bot's admin rights allow. Both can read the chat's history from what RealTimeX recorded since the chat was linked. Replies with `--reply-to`, reactions and the member list now work on both. Every message, including the agent's own, carries a reference to reply, react or act on. Actions that reach beyond the chat, such as leaving a group, blocking someone or changing the profile or bot settings, ask you first in the usual permission prompt. Credentials, payments and business features stay off limits, and a workspace never sees another workspace's chats. Forwarding now goes only to chats the account already serves for the workspace, on every channel.
- **Agents can do almost everything in a Zalo Personal chat** (issue #3022, covers #3024): an agent answering a Zalo Personal chat can now use nearly all of Zalo through `channel-act`: add or remove group members, manage the group and its invite link, forward and delete messages, send videos, voice messages and contact cards, react, send files, set reminders and notes, and read history page by page, including direct messages (from what RealTimeX recorded since the chat was linked). Actions that reach beyond the chat or cannot be undone, such as leaving a group, blocking someone or changing the account profile, ask you first in the usual permission prompt. Account credentials, bank and business catalog features stay off limits, and a workspace never sees another workspace's chats. Messages the agent sends come back with a reference it can use to recall or react to them, and changing one group setting leaves the others as they were.
- **Agents can read history, send stickers, run polls and recall their own messages in Zalo Personal chats** (issue #3005, covers #2998): an agent answering a Zalo Personal chat has one new command, `channel-act`, whose controls come from the channel itself. It can list what the chat supports, read the latest messages of a group (oldest first, with who wrote each and refs it can quote or react to), send stickers and link cards, create, vote in and close polls, and recall a message this account sent. Controls that change the account or the group, such as adding admins or leaving, stay off until a later release adds owner approval. Posting text is unchanged. Agents need `@realtimex/pp-cli` 2.0.53 or later.
- **Choose which screen to see in Remote screen**: when the computer you're watching or controlling has two or more screens, the Remote screen header now shows which one you're seeing, such as **Screen 1 · Main**. Open it to pick another screen; each one is listed with its name and size. Screens are numbered left to right, then top to bottom. Switching keeps Control, transfers, the clipboard setting and picture quality, resumes a paused view, and with Control on, your typing goes to the new screen. If a switch fails, the view stays on the screen you had, with **Try again**. If the screen you're viewing is disconnected, the main screen is shown and a note says so. While you watch another screen, a note says when an agent is working on the main screen, with a button to show it. Your choice lasts while the panel is open, also after a reconnect; a new panel opens on the main screen. This needs a RealTimeX Link version that can switch screens on the controlled computer; with an older Link, or a single screen, Remote screen looks as before.
- **Start with this computer**: on Windows and macOS, a RealTimeX administrator can turn on **Start with this computer** in Settings → Interface. RealTimeX Link then starts when the computer starts, before anyone signs in, so you can reach the computer by remote control at the sign-in screen and after a restart. Turning it on asks once for the computer's administrator password (on Windows, the RealTimeX installer sets up Link's service). Turning it off needs no password. On macOS, Login Items lists it under RealTimeX.AI. Linux isn't supported yet, so the setting is hidden there.

## Changed

- **Pancake agents see your staff's replies and decide when to answer**: on a Pancake channel where the agent decides what to post, replies your staff send from Pancake now reach the agent, as they already do on Zalo, WhatsApp and Messenger. The agent won't repeat or contradict them and can follow up on what staff promised. Customer messages are no longer held back for a fixed time after a staff reply, so a customer who writes after staff have left is no longer missed: the agent decides when to answer, waits while staff are handling a chat, and can check back a few minutes later if nobody did. Tell it how long to wait in its guidance, for example "give staff 10 minutes during office hours and 3 minutes at night". The pause tag (`ai-off` by default) still keeps the agent out of a conversation, and a reply it tries to send there is refused. The "quiet window after a staff reply" setting is gone from Settings; it still applies only to Pancake channels on Platform delivery. Agents need `@realtimex/pp-cli` 2.0.62 or later for the updated help.
- **macOS:** Upcoming versions of RealTimeX will need macOS 13 Ventura or later. Macs on macOS 12 Monterey can keep using the last version released before then. RealTimeX will show "Update needs macOS 13" instead of offering an update it can't install.
- **RealTimeX now runs on Node.js 24**: the Node.js that RealTimeX installs for its own server, its terminals and Local Apps moves from version 22 to 24.22.2, which is supported until April 2028. On macOS and Linux, the first launch after this update downloads Node.js 24 once, so it needs an internet connection; on Windows, the installer downloads it. After that first launch, RealTimeX reinstalls everything that was installed globally with npm under Node.js 22, such as Codex, Grok, `realtimex-pp-cli` and the CLIs you installed from RealTimeX, from the npm registry at the same version. It does this once, in the background, and it takes a few minutes and an internet connection; until it finishes, those commands aren't found in RealTimeX terminals. Anything it couldn't reinstall is listed in the System Log with the command to install it yourself. Projects you set up in a RealTimeX terminal whose packages include compiled native add-ons may need `npm rebuild` or a fresh install. On Windows, the Node.js that nvm-windows makes available to the whole computer also moves to 24.22.2, so other projects that use it get version 24 too. Node.js 22 stays on your computer, but RealTimeX no longer uses it.
- **See what stops before an update restarts RealTimeX**: when an update is ready, the update dialog now lists what a restart would stop: agents that are working, terminal sessions, Local Apps, unsent messages, uploads, documents being added and recordings. Each one says what will happen, such as whether a terminal session reopens afterwards, and a switch chooses whether sessions and Local Apps come back. If something new starts while the dialog is open, **Restart now** doesn't restart; the dialog shows the updated list instead. Anything RealTimeX couldn't check is listed as such. Update restarts no longer show the separate quit warning, and cancelling a quit no longer leaves an update set to install the next time you quit.
- **The update dialog names what it's setting up**: while an update prepares, the Set up step now says whether it's downloading app components or the local AI runtime.
- **Know whether the last update finished**: after **Restart now**, RealTimeX says **Updated to version X.** once it's running again on the new version, and only once. If it opens again on the old version instead, it says the update didn't finish, and the title bar shows **Update didn't finish** until you open it. The dialog says why when RealTimeX knows, such as background processes that wouldn't close, and otherwise what might have happened. **Try again** checks for the update again; neither button installs anything by itself.
- **Clearer advice when Windows asks for permission to update**: the Windows notice in the update dialog now says what happens if the administrator request isn't approved, which covers a request that was declined, never answered or never seen. To keep using your current version, choose **No** if Windows is still asking, then open RealTimeX from the Start menu. The notice also says that Windows may show the request outside a remote session, so you may need to answer it on that computer. When an update didn't finish on Windows, the dialog gives the same advice.

## Fixed

- **Pancake and Messenger customers no longer get an English "couldn't process the uploaded file" message**: when a customer sent something RealTimeX couldn't use, such as a message card, a sticker or a photo that failed to download, it posted that notice in the customer's chat. On Pancake even an ordinary text with a place name could trigger it, because Pancake attaches the address it detects. Customers on Pancake and Messenger now never see such a notice. It goes to the System Log as a warning with the attachment type and reason, so you still see it. The agent still gets the customer's message and is told what it could not open, so it can answer the rest. On Messenger the agent now answers these messages instead of skipping them. Other channels keep showing the notice as before.
- **The agent understands more of what Pancake customers send**: a Facebook like (👍) reaches the agent as a 👍. Pancake's detected address is added to the customer's text. A card's title, text and buttons are passed on when Pancake provides them. When Pancake returns a card without its text, such as a quick reply the customer tapped, an agent that decides its own replies is told so, along with how soon it came after the customer's previous message, so it can ask; with Platform delivery such a card starts no turn. Videos and voice messages are named so the agent can ask about them, including voice notes and files that Pancake sends without a type. Photo and file links on Facebook's servers, including redirects, now download, and a file over the size limit is named as too large so the agent can explain it. When a customer comes from an ad, the agent sees which ad, the same way as on Messenger. The agent's view of the conversation history shows the same details. Attachment types RealTimeX doesn't know yet are named in the turn and logged as a warning instead of being dropped.
- **Codex keeps its hook approval when another RealTimeX runtime starts Codex**: RealTimeX's Codex hook settings no longer name the Node and bridge files of the RealTimeX that launched Codex. Each session now passes its own through its environment. So a worktree or development runtime, or an update that moves the app's Node, no longer rewrites the shared Codex profile and drops the approval for the other runtime's sessions, which then stopped at "Hooks need review" before reading their first prompt. After this update, Codex asks to review RealTimeX's hooks once. A runtime without this change can still rewrite the profile until it is updated too.
- **Keyboard focus stays in the title bar after the update dialog closes**: closing the update dialog with **Later** or Escape now returns focus to the update button, or to the About button when no update button is left, also when the dialog was opened from the tray. Before, focus could be lost after an update that didn't finish. On macOS the About button now shows a focus ring and is read out by its version.
- **Customers no longer get a false "Sorry, something went wrong"**: on a busy computer, a Pancake customer could get "Sorry, something went wrong. Please try again." a few seconds after writing, followed by the agent's real reply. RealTimeX now gives the agent up to a minute to pick up a chat message on every channel, and a message that only took longer is no longer treated as a failure. Messenger and Pancake customers never see system or error messages, or the agent's progress updates ("Terminal agent is working…"), even when a chat's output is set to Verbose, and also when you start the work from the desktop; RealTimeX's System Log keeps them. People you paired and your own team still see them as before.
- **Agents no longer repeat a channel change or message by accident**: when a chat platform refused an agent's action, such as adding a Pancake tag that doesn't exist, the request was sent up to three more times. When the platform didn't answer in time or the connection dropped, the action or message could be sent again and show up twice. Refused actions are now never repeated. Anything the platform didn't confirm comes back to the agent as "may have been applied", so it checks the chat before trying again.
- **A saved computer's Remote computer secret keeps its name**: connecting again to a computer you'd already saved, or RealTimeX signing in to it again in the background, replaced its Remote computer secret with a new one under a slightly different name, for example `rc-office-mac` and `rc-office-mac-69fb37` in turn. An agent in the middle of a task then failed with "A referenced secret does not exist" until it looked the secret up again. RealTimeX now updates the existing secret in place, so its name stays the same. A new secret is saved only when the old one was deleted.
- **Agents can control computers you added through your RealTimeX account**: a computer you connected without its password, because it's signed in to the same account, worked when you watched it but not for agents: its Remote computer secret had no key, so agents couldn't sign in. Agents now sign in to it with your account, the way watching it does, with nothing new stored for them. They stop when you sign out of RealTimeX, when the computer is removed from Computers you can control, or when its secret isn't available in that workspace. If the other computer asks before letting computers in, agents say so and leave nothing waiting there. Client-isolated workspaces still need a computer added with its password.
- **Agents can use apps by their controls on Linux**: on Linux, RealTimeX installed RealTimeX Link without the part that reads apps' buttons, fields and menus, so agents controlling a Linux computer were told it "has no accessibility layer" and could only use screenshots and clicks. RealTimeX now installs it with Link. A Linux computer that already has the same Link version gets it with the next RealTimeX Link update. macOS and Windows weren't affected.
- **Remote screen says when remote control isn't available, instead of "Lost connection"**: when the other computer is on and reachable but RealTimeX Link there has no remote control helper running (for example right after Link updated itself on a Mac), the live view now names that computer, saying for example "Remote control isn't available on Office-Mac right now", and suggests asking someone at it to sign out and back in, or to restart RealTimeX Link there, with **Try again**. Before, it said the connection was lost and to check that the computer is on. Agents get the same reason with a suggestion instead of a generic error. This needs RealTimeX Link 0.6.1 or later on the controlled computer; RealTimeX now includes Link 0.6.1, which also restarts its macOS remote-control helper after it updates itself, so remote control no longer stops working after a Link update until someone signs out.
- **A Codex agent that asks you a question and then stops now gets your answer**: when a Codex agent asked you something and ended its turn without writing a reply, the chat kept showing it as working, and your answer waited until you sent another message. RealTimeX now sees that the turn ended, so the agent shows as waiting on you and your answer reaches it right away. Nothing new appears in the chat for a turn with no reply.
- **Zalo Personal agent controls are more dependable**: an agent can now set an auto-reply to repeat daily, on chosen weekdays, or only once, instead of always daily. Sending a video or voice message from a web address no longer makes a request from your computer to that address first. A sticker or other control sent again after a message, file or reaction is sent again instead of being skipped as a repeat, and an error from Zalo while listing reminders is reported instead of being shown as an empty list.
- **Built-in plugins such as Loops no longer go missing after a busy start**: if RealTimeX was busy while starting, a built-in plugin could fail to load and stay unavailable until you restarted the app. For Loops, every loop command then failed with "Plugin route not found", and reloading the plugin was refused. RealTimeX now doesn't rewrite plugins that are already up to date when it starts, retries when the database is briefly busy, and reloading such a plugin now repairs and loads it without a restart.
- **RealTimeX no longer slows down on long agent sessions**: when an agent session had collected thousands of approval events, every time its thread or Mission Control was opened or refreshed, RealTimeX re-read that session's whole history, keeping the computer's processor busy while everything else in the app waited: threads loaded slowly and some requests timed out. RealTimeX now remembers each session's summary and reads only what changed, so on a session with 11,000 approvals a refresh takes a few hundredths of a second instead of 16 seconds. The first time a long session is opened after RealTimeX starts still takes about 2 seconds. The first start after updating can take about 10 seconds longer when you have a lot of agent history, while RealTimeX prepares this once.
